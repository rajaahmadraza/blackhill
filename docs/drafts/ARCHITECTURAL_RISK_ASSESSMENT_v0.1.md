# Blackhill ATS — Architectural Risk Assessment v0.1

Date: 2026-11-01 · Scope: the risks of adapting PMS ATS into the proposed Blackhill platform. Likelihood and impact are my
judgement (L/M/H), not measurements. "Blocks MVP" = the first operational release cannot responsibly ship until it is mitigated.

| # | Risk | Impact | Likelihood | Mitigation | Blocks MVP? |
|---|---|---|---|---|---|
| R1 | **CNIC identity is pervasive.** 57 non-migration files under `apps/` mention CNIC; sign-in, OTP, throttles, completeness, snapshots, two whole apps (`intake`, `interview_import`, ~5.5k LOC) and ~58 test files assume it. A partial replacement leaves hidden CNIC/Pakistan assumptions (e.g. `\+923…` validator, NOT NULL snapshot columns) reachable in US flows. | H | H | Slice 0 removes CNIC-keyed apps first; S1 replaces identity behind one service; add grep gate + behavioural test that no PK validator is reachable; migration reset (D-06) removes the columns rather than leaving nullable ghosts | Yes |
| R2 | **Unknown test baseline.** ~2,760 test methods exist in the audit; none has been run in this repo, many embed CNIC fixtures. Mass rewrites tempt weakening or skipping tests ("do not weaken validation to make tests pass"). | H | H | S0 records a real baseline before any change; deleted tests only for removed modules; every other failure fixed or rewritten with equal strength; track test count per risk area (auth, authorization, snapshots, documents) and never reduce it silently | Yes |
| R3 | **Lifecycle conflation inherited from PMS.** `Application.final_outcome` stores placement results; offers are bound to Applications; Application stages encode SELECTED/INTERVIEW. Building submissions on these shortcuts would force destructive migrations later and make Scenario E unrepresentable. | H | M | Separate entities (Consideration, ClientSubmission, Offer re-parented, Placement); stop writing `final_outcome`; code-defined status sets with CHECKs; Domain Model scenarios A–H become acceptance tests | Yes (for submissions) |
| R4 | **Credential false-positive.** A feature that reads "uploaded licence = verified" or a free status column would present unverified clinicians to facilities, with legal and reputational consequences, and cannot be unwound without re-verifying everyone. | H | M | Evidence ladder with derived status; no status column; "Verified" rendered only with source + as-of date; packet shows level as of submission; verification rows immutable; tests in S2/S6 | Yes |
| R5 | **Sensitive-data posture is weak and policy is unsettled.** No encryption at rest beyond storage layer (CNIC is plain text today), no AV scan, no staff MFA, no field-level encryption, SSN policy unapproved (A-12), retention/deletion unsettled (D-20). A shortcut that stores SSN/last-four on the profile would be hard to retract. | H | M | SSN excluded from all slices until D-18; separate `onboarding` design with AEAD; staff TOTP before real data; retention decision before launch; counsel review list (Arch §9.4); reveal/audit pattern reused, storage pattern **not** | Yes (MFA, retention); SSN no |
| R6 | **Shared candidate/staff session cookie** (verified: one default `sessionid`, one store). Violates the intent of the "separate security domains" invariant; staff logout flushes candidate state; a staff user testing as a candidate carries both identities. | M | H (already true) | Hostname split + path guards (D-05/D-28); tests for cookie scoping and logout independence | Yes (before real data) |
| R7 | **Scope creep and over-engineering by a solo AI-assisted process.** The ambition (Bullhorn/LaborEdge-class) is large; the inherited 62k-LOC, 17-app base is already big; agents may add generic frameworks, tenancy, or integrations "for the future". | H | M-H | Release split in Arch §14; explicit do-not-build list per module (Arch §13); decision tiers gate slices; each slice has a demo criterion for Ahmad; no new infrastructure without measured need | No (process risk) but affects everything |
| R8 | **Repository hygiene and provenance gaps.** The directory is not a git repo, `PROVENANCE.md` is missing, `compose.production.yml`/nginx/scripts/runbook are still PMS-named, and the audit found untracked candidate-document folders in the PMS tree (copied tree could carry real data; this tree has `private_uploads/` containing **11 files** and an empty `public_uploads/`; I counted files only and did not open them, so whether they are synthetic is unknown). | M | H | Initialise local git with no remote and write PROVENANCE (S0); inspect/empty `private_uploads/` against the synthetic-data rule before first commit; rewrite deployment files before any deployment; keep `.env`/uploads ignored | Yes (provenance, uploads check) |
| R9 | **Scheduler and integration absence.** No scheduler, only an EMAIL channel, no timeline. Credential-expiry alerts (a stated requirement) and dialer/e-sign need new mechanisms; picking Celery/Redis prematurely adds ops burden for a 1–5-person shop; omitting idempotency in cron jobs causes duplicate alerts. | M | M | Cron + idempotent management commands (P-10); idempotency keys per credential/window; adapter interfaces only when a second implementation or callback exists | No (alerts are S7 follow-up) |
| R10 | **Time and locale defaults wrong for the US.** `TIME_ZONE=Asia/Karachi`, bilingual publish rule, PKR labels. Date-only concepts (credential expiry, start dates) evaluated in UTC or the wrong zone give off-by-one-day expiry decisions in a compliance-sensitive product. | M | H (already true) | Env-set company timezone; facility IANA timezone; `DateField` semantics (P-12); boundary tests in S2/S7 | Yes (for credentials) |

## Notes on interpreting the table

- **Why R3 is "Likelihood M":** the conflation exists in code today; the risk materialises only if submissions or offers are built on
  top of it, which this design explicitly avoids.
- **R5 distinguishes** items that block MVP (MFA, retention) from SSN, which stays out of MVP entirely under A-12.
- **Not rated because not evidenced:** PMS code quality at scale (the suite's last recorded state is unknown); performance (no data
  volumes yet; Arch §12.9 sets the indexing posture and the rule to measure before adding infrastructure).
- **Dependencies between risks:** R1 and R2 are the same work seen from two sides (removing CNIC changes many tests); schedule them
  as one slice (S0/S1) and track the test-count rule in R2 while doing R1.
